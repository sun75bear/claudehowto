# 6. 実例集（コードを書く人向け）

!!! info "コードを書かない方は飛ばして構いません"
    このページは開発作業をする人向けです。[7. 使いこなす](07-power-up.md) へ進んでください。

Claude Code はもともとこの用途のために作られています。4例に絞って紹介します。

---

## 例1: バグの原因調査と修正

```text
このエラーが出ています。原因を調べて直してください。

- 関連するファイルを自分で探して読んでください
- 直したらテストを実行して、通ることを確認してください
- 何が原因だったかを最後に説明してください

〈エラーメッセージ / スタックトレースを貼る〉
```

呼び出し元をたどる、ログを読む、修正して実行し直す——この往復を自分で回します。**「テストを実行して確認まで」**と書くのが肝で、これがないと動作未確認の修正案が返ってきます。

---

## 例2: テストを書かせて、失敗を直させる

```text
〈src/auth〉のテストを書いてください。

- 既存のテストと同じ書き方・同じディレクトリ構成に合わせてください
- 正常系だけでなく、境界値と異常系も入れてください
- 書いたら実行して、失敗するものがあれば原因を調べて直してください
```

後回しにされがちな作業の代表格です。既存のテストを読んで書き方を揃えてくれるので、レビューの負担も小さくなります。

---

## 例3: リファクタリング

```text
〈このモジュール〉をリファクタリングしたいです。

まず Plan モードで、何をどう変えるかの方針だけ出してください。
ファイルはまだ変更しないでください。

- 外部から見た振る舞いは変えない
- 変更はテストが通ることで担保してください
```

**大きな変更は必ず Plan モードから**始めてください。方針を合意してから実行させると、やり直しが激減します。

---

## 例4: コミットと Pull Request

```text
今の変更をコミットして、Pull Request を作ってください。

- コミットは論理的な単位で分けてください
- コミットメッセージには「なぜ」を書いてください
- PR の説明には、変更点・テスト方法・レビューで見てほしい点を含めてください
```

Git の操作をそのまま任せられます。ブランチを切る、ステージする、メッセージを書く、PR を開く、までが一続きです。

---

## そのほか

- **CI の失敗調査** — 失敗したジョブのログを渡して原因を追わせる
- **依存関係の更新** — 更新して、壊れた箇所を直させる
- **コマンドラインとの組み合わせ** — `git diff main --name-only | claude -p "変更ファイルをセキュリティ観点でレビューして"` のようにパイプで繋げます（ターミナル版）
- **GitHub Actions との連携** — PR レビューや Issue の仕分けを自動化できます

詳しくは公式の [よくあるワークフロー](https://code.claude.com/docs/en/common-workflows) と [ベストプラクティス](https://code.claude.com/docs/en/best-practices) を参照してください。
